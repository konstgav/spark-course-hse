# Данные курса: розничная сеть

Синтетические данные сети продуктовых магазинов: около 150 магазинов в 34 городах и 15
регионах России, от Москвы до Хабаровска. Кассы каждый час выгружают операции в CSV-файл,
а хранилище загружает эти файлы в Iceberg.

Данные создаёт генератор [generator/generate_retail.py](../generator/generate_retail.py).
Цифры, города и названия товаров правдоподобны, но выдуманы.

## Как получить данные

```bash
conda activate spark-course
python generator/generate_retail.py                 # из корня репозитория
```

| параметр | по умолчанию | смысл |
|---|---|---|
| `--start` | `2026-09-04` | первый день (пятница: в данные попадают будни и выходные) |
| `--days` | `3` | сколько дней генерировать |
| `--scale` | `1.0` | объём: `1.0` — самый большой часовой файл ~90 МБ, `0.1` — в 10 раз меньше |
| `--seed` | `42` | зерно: с одинаковыми параметрами файлы получаются одинаковыми |
| `--out` | `data/retail` | куда писать |

По умолчанию получается 72 файла (3 дня × 24 часа), около **36 млн строк и 3,1 ГБ**.
Генерация занимает 1–2 минуты. Для отладки берите `--scale 0.1`: 300 МБ за 10 секунд.

Если меняете `--start` или `--days`, поменяйте и `start_date` / `end_date` в
[dags/retail_sales_bronze.py](../dags/retail_sales_bronze.py).

## Файлы

```
data/retail/
├── dims/
│   ├── stores.csv          магазины
│   ├── categories.csv      категории товаров
│   └── products.csv        товары
└── sales/
    ├── sales_2026-09-04T00.csv     операции, выгруженные в час 00:00-01:00 по Москве
    ├── sales_2026-09-04T01.csv
    └── ...                         по файлу на каждый час
```

Все файлы — UTF-8, разделитель запятая, первая строка — заголовок. В справочниках
текстовые поля с запятыми взяты в двойные кавычки (при чтении Spark нужен `escape='"'`).
Пустое поле означает `NULL`.

Внутри Docker каталог `./data` виден как `/opt/data` (Spark и Airflow), поэтому джобы
читают файлы по адресу `file:///opt/data/retail/...`.

## Факт: `sales_*.csv` — операции касс

Одна строка — одна позиция чека (или операция над ней).

| поле | тип | пример | описание |
|---|---|---|---|
| `event_id` | bigint | `118100882` | уникальный идентификатор операции — **ключ** |
| `event_ts` | timestamp | `2026-09-05 15:00:04.413` | время операции, **по Москве**, до миллисекунд |
| `receipt_id` | bigint | `52591233` | номер чека: все позиции одной покупки |
| `line_no` | int | `3` | номер позиции в чеке |
| `store_id` | int | `51` | магазин → `stores.csv` |
| `product_id` | int | `779` | товар → `products.csv` |
| `category_id` | int | `9` | категория товара → `categories.csv` |
| `customer_id` | bigint, **может быть пустым** | `143847` | покупатель. Известен, если покупатель показал карту программы или оплатил привязанной картой (~60% чеков) |
| `is_loyalty` | boolean | `true` | покупатель — участник бонусной программы |
| `operation_type` | string | `SALE` | тип операции, см. ниже |
| `quantity` | int | `2` | количество, шт. |
| `price_regular_kop` | bigint | `29580` | стоимость позиции **без скидки**, коп. (цена за штуку × количество) |
| `price_paid_kop` | bigint | `28101` | итоговая стоимость позиции **со скидкой**, коп. |
| `payment_method` | string | `CARD` | способ оплаты чека, см. ниже |
| `ref_event_id` | bigint, может быть пустым | `118100455` | для `CANCEL` и `RETURN` — `event_id` исходной продажи |

Суммы хранятся в копейках, целыми числами: так нет ошибок округления, как у `float`.

### Типы операций `operation_type`

| значение | что произошло | особенности |
|---|---|---|
| `SALE` | товар продан | |
| `CANCEL` | кассир отменил (сторнировал) позицию до закрытия чека | тот же `receipt_id` и `line_no`, через 20 секунд — 5 минут после продажи. `ref_event_id` → отменённая продажа. Суммы положительные, те же, что у продажи. Отмена может попасть в следующий часовой файл |
| `RETURN` | покупатель вернул товар | через 2 часа — 5 дней после покупки, **новым** чеком. `ref_event_id` → исходная продажа. Суммы положительные |

Отмены — около 1,5% позиций, возвраты — около 0,5%.

### Способы оплаты `payment_method`

| значение | что это |
|---|---|
| `CARD` | банковская карта |
| `SBP` | Система быстрых платежей (QR-код) |
| `CASH` | наличные. Доля зависит от региона: 8% в Москве, до 22% в регионах |
| `BONUS` | оплата бонусными баллами, только участники программы |

Способ оплаты общий для всех позиций чека.

### Как устроены данные: что можно найти

* **Суточный цикл.** Пик покупок — вечер по местному времени. Магазины открыты с 7–8 до
  23 часов по местному времени. `event_ts` — московское время, поэтому Хабаровск и
  Владивосток торгуют, когда в Москве ночь.
* **Выходные.** В субботу покупок примерно на 20% больше, чем в будни.
* **Средний чек** выше в гипермаркетах, в Москве, Санкт-Петербурге и на Дальнем Востоке
  (выше цены). У участников бонусной программы корзина больше.
* **Скидки.** Каждый день около 12% товаров в промо со скидкой 10–35%, участники программы
  иногда получают ещё 5%.
* **Популярность товаров** неравномерна (закон Ципфа): в каждой категории несколько
  хитов и длинный хвост.

## Известные дефекты источника

Как в настоящих выгрузках, данные «грязные». Каждый дефект сделан намеренно.

| дефект | доля | как выглядит | как обработать |
|---|---|---|---|
| Дубли внутри файла | ~1% строк | строка повторяется целиком, с тем же `event_id` | оставить одну строку на `event_id` |
| Повторная отправка | ~0,5% строк | строки предыдущего часа ещё раз приходят в следующем файле | то же: дедупликация по `event_id` уже **между** загрузками — `MERGE INTO` |
| Опоздавшие строки | ~2% чеков | офлайн-касса выгрузила чек на 1–3 часа позже (его отмены — иногда на 4): `event_ts` раньше часа файла | ничего не терять: операция принадлежит часу `event_ts`, а не часу файла |
| Отрицательная цена | ~0,007% | `price_paid_kop < 0` | отбросить |
| Неизвестный магазин | ~0,007% | `store_id = 9999`, его нет в справочнике | отбросить |
| Нет товара | ~0,007% | пустой `product_id` | отбросить |

## Слои хранилища

```
data/retail/sales/*.csv
      │  DAG retail_sales_bronze: каждый час, jobs/retail/load_sales_bronze.py
      ▼
iceberg.retail.sales_bronze      как в файле + file_hour, source_file, loaded_at
      │  ноутбук занятия 2: очистка + MERGE INTO
      ▼
iceberg.retail.sales_silver      без дублей и битых строк, отмены применены
      │  ноутбук занятия 3 / DAG retail_mart_*
      ▼
Postgres dwh.public.mart_*  ──▶  Metabase
```

Справочники загружает DAG `retail_dims` в таблицы `iceberg.retail.stores`, `categories`
и `products`.

### `iceberg.retail.sales_bronze`

Все поля файла без изменений, плюс служебные:

| поле | описание |
|---|---|
| `file_hour` | за какой час пришёл файл. Таблица партиционирована по этому полю (`hours(file_hour)`) |
| `source_file` | имя файла |
| `loaded_at` | время загрузки |

Загрузка часа перезаписывает партицию этого часа (паттерн **Data Overwrite**), поэтому
перезапуск не создаёт дублей.

### `iceberg.retail.sales_silver`

| отличие от bronze | |
|---|---|
| строки | только `SALE` и `RETURN`, по одной на `event_id`, без битых |
| `is_cancelled` | `true`, если продажу отменил кассир (была операция `CANCEL`) |
| `event_date` | дата операции, `to_date(event_ts)`. Таблица партиционирована по ней |
| нет колонок | `file_hour`, `source_file`, `loaded_at` |

Обновляется командой `MERGE INTO` по `event_id` (паттерн **Merger**): повторный запуск
ничего не дублирует.

## Метрики

| метрика | формула |
|---|---|
| Выручка (чистая) | `SUM(price_paid_kop)` по `SALE` с `NOT is_cancelled` **минус** `SUM(price_paid_kop)` по `RETURN` |
| Выручка без скидок | то же по `price_regular_kop` |
| Скидка | выручка без скидок − выручка |
| Число чеков | `COUNT(DISTINCT receipt_id)` по `SALE` с `NOT is_cancelled` |
| Средний чек | выручка продаж / число чеков (возвраты не участвуют) |

Возврат уменьшает выручку **в день возврата**, а не в день покупки: так считает бухгалтерия.
