## Путь данных сегодня

```
iceberg.retail.sales_silver      ~35 млн строк, HDFS
        │  Spark SQL: агрегаты
        ▼
датасет                          одна строка = один объект (магазин, чек)
```

* Модель учится на **датасете**, а не на сырых операциях: сначала данные сворачивают до уровня объекта
* Тяжёлая часть — сборка датасета — та же, что у витрин: Spark SQL и агрегаты

## Машинное обучение в одном слайде

| термин | что это | пример |
|---|---|---|
| **объект** | то, про что делаем прогноз | чек, магазин, магазин × час |
| **признаки** | что известно об объекте заранее | формат магазина, число позиций в чеке |
| **целевая переменная** | что хотим предсказать | выручка, «участник программы» |
| **обучение** | подбор параметров модели по примерам с ответами | `model.fit(X, y)` |
| **прогноз** | применение модели к новым объектам | `model.predict(X_new)` |

* **С учителем:** в истории есть правильные ответы — регрессия (число) и классификация (класс)
* **Без учителя:** ответов нет, модель ищет структуру сама — кластеризация

## Датасет: одна строка = один объект

```sql
SELECT s.store_id, st.format, st.region, s.event_date,
       hour(s.event_ts)                            AS hour_msk,     -- признаки
       CAST(SUM(s.price_paid_kop) / 100 AS DOUBLE) AS revenue_rub   -- целевая переменная
FROM iceberg.retail.sales_silver AS s
JOIN iceberg.retail.stores AS st ON st.store_id = s.store_id
WHERE s.operation_type = 'SALE' AND NOT s.is_cancelled
GROUP BY s.store_id, st.format, st.region, s.event_date, hour(s.event_ts)
```

* 35 млн операций → 6 900 строк «магазин × час»: такой датасет помещается в pandas
* Текстовые признаки модель не понимает: **one-hot** превращает `format` в колонки 0/1
* `drop_first`: одна категория выбрасывается и становится точкой отсчёта для коэффициентов

## Утечка данных и честная проверка

**Утечка** — признак, который на истории почти равен ответу, но в момент прогноза недоступен.

* `customer_id` известен почти только у участников программы: на истории качество отличное
* а применять модель будем к **анонимным** чекам — там `customer_id` всегда пуст

**Проверка** — только на данных, которых модель не видела: train и test.

| разбиение | когда |
|---|---|
| **по времени**: учимся на 4–5 сентября, проверяем на 6-м | прогноз будущего: выручка по часам |
| **случайное** 80 / 20 | объекты независимы: чеки одного дня |

## Метрики регрессии

| метрика | смысл | хорошо |
|---|---|---|
| **MAE** | средняя ошибка, в рублях | меньше |
| **R²** | доля разброса, которую объясняет модель | ближе к 1 |
| **базовая линия** | прогноз «всегда среднее»: MAE без модели, R² = 0 | модель должна быть заметно лучше |

| модель | MAE, руб. | R² |
|---|---|---|
| среднее | 894 000 | 0,00 |
| линейная регрессия | 365 000 | 0,80 |
| случайный лес | 153 000 | 0,96 |

Линейная модель видит в часе одно число «+30 тыс. руб. за час». Деревья находят вечерний пик и ночь в Хабаровске сами.

<!-- _class: theory -->

## Метрики классификации

Матрица ошибок для 360 тыс. чеков test:

| | прогноз 0 | прогноз 1 |
|---|---|---|
| **не участник** | 107 тыс. ✔ | 53 тыс. ✘ |
| **участник** | 51 тыс. ✘ | 145 тыс. ✔ |

* **Accuracy** — доля верных ответов (0,71). Обманчива, когда классы несбалансированы
* **Precision** — из отмеченных моделью сколько действительно участников; **recall** — какую долю участников нашли
* **ROC AUC** — шанс, что чек участника получит вероятность выше, чем чек не-участника (0,78). 0,5 — монетка
* Модель выдаёт **вероятность**, класс — это вероятность ≥ 0,5. Порог можно двигать

## sklearn или Spark ML

| | sklearn | Spark ML |
|---|---|---|
| где данные | pandas, память одного компьютера | Spark DataFrame, весь кластер |
| объём | до миллионов строк | сколько поместится на кластер |
| алгоритмы | сотни, удобные графики | основные: линейные, деревья, бустинг, k-means |
| признаки | матрица `X` | одна колонка-вектор `features` |
| типичный путь | Spark собирает датасет → `toPandas()` → sklearn | всё внутри Spark |

Правило: датасет маленький — sklearn; большой или модель нужна в DAG — Spark ML.

## Pipeline в Spark ML

```python
pipeline = Pipeline(stages=[
    StringIndexer(inputCols=["payment_method", "format"], outputCols=[...]),   # строка -> номер
    OneHotEncoder(...),                                                        # номер -> вектор 0/1
    VectorAssembler(inputCols=["items", "amount_rub", ...], outputCol="raw_features"),
    StandardScaler(inputCol="raw_features", outputCol="features"),
    LogisticRegression(labelCol="label", featuresCol="features"),
])
model = pipeline.fit(train)          # Estimator -> PipelineModel
predictions = model.transform(test)  # + probability, prediction
```

* **Estimator** учится (`fit`), **Transformer** добавляет колонки (`transform`)
* Подготовка признаков — часть модели: сохраняется и применяется вместе с ней
* `model.write().save(path)` → `PipelineModel.load(path)` в другом скрипте

## Кластеризация: k-means

Алгоритм: k случайных центров → каждый магазин к ближайшему центру → центр в среднее своих магазинов → повторять.

* **Масштабирование обязательно:** чеков в день — тысячи, доля наличных — единицы. Без `StandardScaler` расстояние считал бы только поток
* **Число k** задаёт аналитик: silhouette (−1…1, чем больше, тем чётче границы) + можно ли назвать каждый сегмент
* **Номера кластеров случайны** — перенумеровываем по понятному правилу (дневная выручка), иначе графики «прыгают»

| k | silhouette | размеры сегментов |
|---|---|---|
| 4 | 0,67 | 18, 24, 25, 82 |
| 7 | 0,76 | 4, 7, 14, 18, 24, 33, 49 |

## Модель в продакшене: переобучение по расписанию

```python
with DAG(dag_id="retail_ml_store_segments",
         schedule="0 6 * * 1",        # cron: каждый понедельник в 06:00
         catchup=False,               # только последняя неделя, не все с start_date
         params={"k": 4}) as dag:
    SparkSubmitOperator(application="/opt/jobs/retail/ml_store_segments.py",
                        application_args=["--k", "{{ params.k }}", "--model-date", ...], ...)
```

| что | куда | зачем |
|---|---|---|
| модель | HDFS `/models/store_segments/<дата>` | версия на каждую неделю, можно откатиться |
| сегменты и профили | Postgres `ml_store_segments`, `ml_segment_profile` | дашборд |
| журнал запусков | Postgres `ml_runs`, **append** | видно, не испортилось ли качество |

## Итоги занятия

* Модель учится на **датасете**: Spark сворачивает миллионы операций до строки на объект
* Регрессия прогнозирует число, классификация — класс, кластеризация ищет группы без ответов
* Качество — только на отложенных данных и в сравнении с **базовой линией**; признаки с утечкой — исключить
* Маленький датасет — **sklearn**, большой или для DAG — **Spark ML Pipeline**
* Модель в продакшене переобучается **по расписанию**, хранит версии и журнал качества
* Результат модели — таблица в Postgres, её показывает Metabase, как любую витрину
